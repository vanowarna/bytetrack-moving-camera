The idea

A moving camera looks like everyone is moving

ByteTrack predicts each person with a constant-velocity Kalman filter in image coordinates, then matches predictions to detections by overlap (IoU). When the camera pans, every box shifts, even for people standing still. Where does that hurt?

Try it: how far can a prediction drift before matching fails?

Illustration, not measured data. A person stands still; the camera pans by s pixels per frame. The filter, unaware of the camera, keeps the box where it was, so the prediction is off by s · k after k frames without a match. ByteTrack accepts a match when IoU > 0.1 (matching threshold 0.9).

IoU between prediction and detection
–

At one frame, even a fast pan keeps the IoU high. After several lost frames the same pan pushes the prediction off the person. That is what the measurements in E3 show.

E1 · Reproduction

The published numbers reproduce exactly

Official code (commit d1bf019), official weights, MOT17 half-val. The paper’s text implies a matching threshold of 0.8, but its numbers come from the code’s default of 0.9.

Metric
this studypublished value

MOTA, IDF1, ID switches: ByteTrack’s own evaluation (py-motmetrics). HOTA: TrackEval. Our HOTA of 67.9 also matches the 67.88 reported for ByteTrack by BoT-SORT [6].

E3 · Mechanism

The prediction suffers, but matching survives. Re-finding fails.

Camera motion is measured per frame (ORB features, people masked, RANSAC similarity fit) and every Kalman prediction is logged without changing a single result.

Lost tracks: the real cost

Show
staticmoving

A lost track’s prediction is extrapolated over several frames. With a moving camera it drifts off the person, so the track comes back with a new ID: that is the larger AssA gap of E2.

Camera motion degrades the one-frame Kalman prediction measurably, but the predicted box still overlaps its detection well enough. The cost appears when a lost track must be found again.

E4 · Sensitivity

The gap persists in all 15 settings

One parameter at a time around the official settings. This is a sensitivity study, not a fix.

Parameter
staticmovingofficial value

Only the Kalman process noise moves the moving-camera result: trusting constant velocity more hurts moving cameras; allowing faster change helps them. The motion model is the part to study next, for example camera-motion compensation [6].

Reproduce

From a clean machine to Table I

Every number in the paper and on this page is generated from the files in results/; none is typed by hand.

Environment (uv, CUDA 12.8)

git clone https://github.com/vanowarna/bytetrack-moving-camera
cd bytetrack-moving-camera
uv sync
bash scripts/setup_external.sh   # Windows: scripts\setup_external.ps1

Weights and data

Place bytetrack_ablation.pth.tar from the ByteTrack model zoo in weights/ and MOT17 in data/mot/ (see README).

Split, then Table I

uv run python scripts/make_splits.py
uv run python scripts/run_many.py --configs "configs/e1_*.yaml" --table e1

E2 – E4 and all paper assets

uv run python scripts/analyze_e2.py
uv run python scripts/run_camera_motion.py --config configs/e1_default.yaml
uv run python scripts/run_e3_log.py --config configs/e1_default.yaml
uv run python scripts/analyze_e3.py --case-seq MOT17-13-FRCNN
uv run python scripts/make_e4_configs.py
uv run python scripts/run_many.py --configs "configs/e4/*.yaml" --table e4
uv run python scripts/analyze_e4.py
uv run python scripts/make_paper_assets.py

Limitations

Seven sequences, so all evidence is correlational; the groups also differ in frame rate, viewpoint and lighting. The camera model is a 2-D similarity transform (no parallax). One detector and one tracker; one parameter changed at a time.
